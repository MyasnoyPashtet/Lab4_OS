## 2. Стратегия

Менеджер публикует план, затем аналитик коммитит спецификацию. По ней разработчик реализует базовые функции и интерфейс, а QA параллельно готовит тест-кейсы. Когда базовая версия передана на проверку, разработчик приступает к функциям 3–4 и исправляет замечания QA по мере поступления.

Когда все четыре функции доступны для проверки, аналитик готовит пользовательскую инструкцию по фактическому интерфейсу, а QA параллельно проводит итоговое тестирование. Найденные дефекты фиксируются в GitHub Issues и проверяются повторно после исправления.

### Запуск

- **Менеджер** добавляет `docs/plan.md`, проверяет назначения в Issues и сообщает команде порядок работ.
- **Аналитик** после публикации плана готовит и коммитит `docs/spec.md` на основе согласованного `OS_Lab4_requirements.md`. В спецификации фиксирует входные параметры, форматы данных, меню и команды, ожидаемый вывод и правила обработки попыток.
- **Разработчик** проверяет окружение Bash. **QA** изучает структуру исходных файлов и подбирает данные для тестов.

### Базовая версия и полная функциональность

В базовой версии отчёты запускались через меню и CLI. В финальной версии после задачи № 13 отчёты запускаются через интерактивное меню командой `bash lab4.sh`.

- **Разработчик** реализует функции 1–2, подключает их к меню и CLI и передаёт базовую версию на проверку через задачи № 2 и № 4. Затем реализует функции 3–4 в задаче № 3.
- **QA** начинает работу по задаче № 8 после публикации спецификации. Промежуточные результаты проверки фиксирует в задачах на соответствующие функции и интерфейс. Для функций 3–4 отдельно проверяет повторные успешные попытки, совпадение дат и фильтр по календарному году.
- **Менеджер** отслеживает замечания, согласует приоритет исправлений и закрывает вехи после подтверждения результатов проверки.

### Стабилизация и защита

- **Аналитик** в задаче № 9 готовит `docs/guide.md` с требованиями к окружению, размещением данных и примерами запуска.
- **QA** повторно проверяет все четыре функции в Linux и Git Bash, оформляет `docs/test-report.md` и закрывает задачу № 8 после фиксации фактических результатов и ограничений проверки.
- **Команда** после стабилизации подтверждает готовность в задачах [№ 5](https://github.com/MyasnoyPashtet/Lab4_OS/issues/5), [№ 6](https://github.com/MyasnoyPashtet/Lab4_OS/issues/6) и [№ 7](https://github.com/MyasnoyPashtet/Lab4_OS/issues/7). **Менеджер** проверяет комплект материалов, проводит репетицию и участвует в защите.

## 4. Правила работы

- В GitHub Issues указываем ответственного, ожидаемый результат и критерий готовности. При передаче на проверку в задаче оставляем ссылку на коммит или pull request, если он использовался.
- Дефект оформляем отдельной задачей с шагами воспроизведения, ожидаемым и фактическим результатом. Из задачи должна быть видна связь с исправлением и повторной проверкой.
- Функцию считаем готовой, когда она запускается по инструкции, соответствует спецификации и имеет зафиксированный результат проверки.
